# 📌 REVIEW 1: Idea, Concept & Database Design

> **Goal for Review 1:** Convince the evaluator that your project solves a realistic problem, has a mathematically sound database design (ER diagram + 3NF), and proper relational integrity.

### 1. Project Title & Problem Statement
- **Title**: College Club Event Management System
- **Problem Statement**: In colleges, student clubs organize events throughout the semester, but registrations and membership tracking are often handled through scattered Google Forms or paper sheets. This leads to:
  - Duplicate registrations.
  - No central tracking of which students belong to which clubs.
  - Students accidentally registering for past or conflicting events.
- **Solution**: A centralized relational database system that tracks students, clubs, events, club memberships, and event registrations with strict integrity constraints and automated business logic.

---

### 2. ER Diagram & Relational Schema
You have **5 Core Entities**:

1. **`STUDENT`** (`student_id` PK, `student_name`, `email` UNIQUE, `department`, `year`)
2. **`CLUB`** (`club_id` PK, `club_name` UNIQUE, `category`, `faculty_coordinator`)
3. **`EVENT`** (`event_id` PK, `event_name`, `event_date`, `venue`, `club_id` FK -> `CLUB`)
4. **`MEMBERSHIP`** (`membership_id` PK, `student_id` FK, `club_id` FK, `join_date`)
5. **`REGISTRATION`** (`registration_id` PK, `student_id` FK, `event_id` FK, `status`, `registration_date`)

#### Entity Relationships:
- **Student — Membership — Club**: Many-to-Many ($M:N$) resolved using associative entity `MEMBERSHIP`. A student can join multiple clubs; a club has many members.
- **Club — Event**: One-to-Many ($1:N$). A club hosts multiple events; each event is hosted by exactly one club.
- **Student — Registration — Event**: Many-to-Many ($M:N$) resolved using associative entity `REGISTRATION`. A student registers for multiple events; an event receives multiple registrations.

---

### 3. Constraints & Integrity Rules (Show this to score high)
Explain that you used all 4 types of database constraints:
1. **Domain Integrity**:
   - `year BETWEEN 1 AND 4` (Checks valid college year).
   - `status IN ('REGISTERED', 'CANCELLED', 'ATTENDED')` (Restricts registration lifecycle).
2. **Entity Integrity**:
   - Primary Keys (`student_id`, `club_id`, etc.) with `GENERATED BY DEFAULT AS IDENTITY` to prevent `NULL` or duplicate keys.
3. **Referential Integrity**:
   - Foreign Keys with `ON DELETE CASCADE` so deleting a club automatically cleans up associated events and memberships without orphaned records.
4. **Uniqueness Rules**:
   - `UNIQUE(email)`: No two students can register the same email.
   - `UNIQUE(student_id, club_id)`: A student cannot join the same club twice.
   - `UNIQUE(student_id, event_id)`: A student cannot register for the same event multiple times.

---

### 4. Normalization (3NF Justification)
Be ready to state this clearly in Review 1:
- **1NF**: Every table has a primary key and all columns have atomic values (no repeating lists or multiple phone numbers in one column).
- **2NF**: Already in 1NF, and there is **no partial functional dependency** (every non-key attribute depends completely on the entire primary key).
- **3NF**: Already in 2NF, and there is **no transitive dependency** (non-key attribute determining another non-key attribute). For example:
  - We do **not** store `club_name` inside `EVENT`; we only store `club_id` and reference `CLUB`.
  - We do **not** store `student_name` inside `REGISTRATION`; we only store `student_id` and reference `STUDENT`.

### 1. Architecture Overview (1-Minute Pitch)
- **Database**: Oracle Database 21c XE (with native thin mode connection via `python-oracledb`).

| Concept | Where it is in your project | Why it matters |

### 4. Cheat Sheet for Tough Questions
- *“Why did you use an associative table for Membership?”*
  $\rightarrow$ Because a Student can join multiple Clubs, and a Club has multiple Students. It is an $M:N$ (many-to-many) relationship which cannot be stored in a single table without redundancy.
- *“What is the difference between your trigger and your stored procedure?”*
  $\rightarrow$ The stored procedure is called by our Flask app with parameters to perform registration. The trigger sits silently in Oracle and fires automatically on `BEFORE INSERT` as a second layer of defense.
- *“Why did you use thin mode in `python-oracledb`?”*
  $\rightarrow$ Thin mode communicates with Oracle Database 21c directly over TCP/IP without requiring Oracle Instant Client or C libraries, making deployment lightweight and simple.

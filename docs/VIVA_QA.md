# 🎓 DBMS Project Viva Q&A Guide
### College Club Event Management System

Use these 15 questions and simple, plain-English answers to prepare for your viva and lab evaluation.

---

### Q1: What is the purpose of this project and what are the main entities in your ER diagram?
**Answer:**
The project is a **College Club Event Management System** designed to let students join college clubs, view upcoming events hosted by clubs, and register for events.
The 5 entities (tables) in the ER diagram are:
1. **STUDENT**: Represents college students.
2. **CLUB**: Represents campus clubs (e.g., Coding Club, Robotics Society).
3. **EVENT**: Represents events organized and hosted by clubs.
4. **MEMBERSHIP**: Associative table representing a student joining a club.
5. **REGISTRATION**: Associative table representing a student registering for an event.

The relationships are:
- A Student **MAKES** a Membership; a Club **GRANTS** a Membership.
- A Club **HOSTS** an Event.
- An Event **RECEIVES** a Registration from a Student.

### Q2: What are Primary Keys and Foreign Keys? Identify them in your schema.
**Answer:**
- **Primary Key (PK)**: Uniquely identifies each record in a table. It cannot be `NULL` and cannot have duplicate values.
  - Examples in our schema: `student_id` in `STUDENT`, `club_id` in `CLUB`, `event_id` in `EVENT`, `membership_id` in `MEMBERSHIP`, `registration_id` in `REGISTRATION`.
- **Foreign Key (FK)**: A column that establishes a link between data in two tables by referencing the Primary Key of another table. It enforces referential integrity.
  - Examples in our schema:
    - In `EVENT`: `club_id` references `CLUB(club_id)`.
    - In `MEMBERSHIP`: `student_id` references `STUDENT(student_id)` and `club_id` references `CLUB(club_id)`.
    - In `REGISTRATION`: `student_id` references `STUDENT(student_id)` and `event_id` references `EVENT(event_id)`.

---

### Q3: What is the difference between a PRIMARY KEY and a UNIQUE constraint?
**Answer:**
- A table can have only **one** Primary Key, but it can have **multiple** Unique constraints.
- Primary Key does not allow `NULL` values. A Unique constraint allows `NULL` values (unless explicitly marked `NOT NULL`).
- In our project, `email` in `STUDENT` is marked `UNIQUE` so no two students can share the same email, and `(student_id, club_id)` in `MEMBERSHIP` has a composite `UNIQUE` constraint to prevent duplicate club memberships.

### Q4: How did you ensure your database is in Third Normal Form (3NF)?
**Answer:**
1. **1NF (First Normal Form)**:
   - Each column contains atomic (single, indivisible) values.
   - There are no repeating groups (e.g., we don't store multiple events as a comma-separated string in the student table).
   - Every table has a primary key.
2. **2NF (Second Normal Form)**:
   - It is in 1NF and contains no partial dependency (every non-key attribute depends on the full primary key).
   - In `MEMBERSHIP` and `REGISTRATION`, we use surrogate primary keys (`membership_id`, `registration_id`), and all attributes depend on them.
3. **3NF (Third Normal Form)**:
   - It is in 2NF and has no transitive dependencies (no non-key column depends on another non-key column).
   - For example, `EVENT` only stores `club_id`. It does not store `club_name` or `faculty_coordinator`, which belong strictly to `CLUB`.
   - `REGISTRATION` only stores `student_id` and `event_id`. Student names and emails are not copied into `REGISTRATION`.

### Q5: Why did you use `GENERATED BY DEFAULT AS IDENTITY` instead of manual IDs?
**Answer:**
`GENERATED BY DEFAULT AS IDENTITY` is the modern Oracle standard (introduced in Oracle 12c and standard in 21c).
It automatically creates an underlying sequence and assigns auto-incrementing numbers (1, 2, 3...) when new records are inserted. This prevents race conditions and duplicate ID insertion errors.

### Q6: What CHECK constraints did you implement and why?
**Answer:**
We implemented two important domain integrity CHECK constraints:
1. `chk_student_year CHECK (year BETWEEN 1 AND 4)`: Ensures that the college student's study year is between 1st year and 4th year.
2. `chk_reg_status CHECK (status IN ('REGISTERED', 'CANCELLED', 'ATTENDED'))`: Restricts the registration status to only allowed lifecycle states.

### Q7: What is the difference between an INNER JOIN and a LEFT JOIN? Where did you use them?
**Answer:**
- **INNER JOIN**: Returns only rows where there is a match in both tables.
  - Used in `club_member_list` to show only members who match both existing students and clubs.
- **LEFT JOIN (LEFT OUTER JOIN)**: Returns all rows from the left table, along with matching rows from the right table. If there is no match, the right side returns `NULL`.
  - Used in `event_registration_count` where we want to list all events even if an event currently has 0 registrations (`COUNT(r.registration_id)` returns 0 instead of dropping the event).

### Q8: What is the difference between `WHERE` and `HAVING` clauses?
**Answer:**
- `WHERE` filters individual rows **before** any grouping or aggregation takes place.
- `HAVING` filters groups **after** the `GROUP BY` and aggregate functions have been calculated.
- Example from our project:
  ```sql
  SELECT c.club_name, COUNT(m.membership_id) 
  FROM CLUB c JOIN MEMBERSHIP m ON c.club_id = m.club_id
  GROUP BY c.club_name
  HAVING COUNT(m.membership_id) >= 2;
  ```
  Here `HAVING` filters out clubs with fewer than 2 members.

### Q9: What is a Database View, and what views did you create?
**Answer:**
A **View** is a virtual table based on the result set of a saved SQL query. It does not store data physically (unless materialized); it simplifies complex queries and enhances security.
We created two views:
1. `event_registration_count`: Joins `EVENT`, `CLUB`, and `REGISTRATION` to display event details along with total registered students.
2. `club_member_list`: Joins `CLUB`, `MEMBERSHIP`, and `STUDENT` to present a unified roster of club members.

### Q10: What is a Stored Procedure, and what does `register_student_for_event` do?
**Answer:**
A **Stored Procedure** is a precompiled collection of PL/SQL statements stored directly inside the database that can accept input and output parameters.
Our procedure `register_student_for_event`:
- Takes `p_student_id`, `p_event_id`, and returns `p_message` (OUT parameter).
- Validates that the student and event exist.
- Checks if the event date has already passed (`event_date < TRUNC(SYSDATE)`). If so, it blocks registration.
- Checks if the student is already actively registered to prevent duplicate entries.
- If previously cancelled, it re-activates the registration; otherwise, it inserts a new row and issues a `COMMIT`.

### Q11: What is a Database Trigger, and what does your trigger do?
**Answer:**
A **Trigger** is a stored PL/SQL block that automatically executes (fires) in response to a specific database event (such as `INSERT`, `UPDATE`, or `DELETE`) on a table.
Our trigger: `prevent_past_event_registration`:
- Defined as: `BEFORE INSERT ON REGISTRATION FOR EACH ROW`.
- Before any row is inserted with status `'REGISTERED'`, it queries the `EVENT` table.
- If the event date is before today (`v_event_date < TRUNC(SYSDATE)`), it calls `RAISE_APPLICATION_ERROR(-20001, '...')` which cancels the transaction immediately.

---

### Q12: What is the difference between a Stored Procedure and a Trigger?
**Answer:**
- A **Stored Procedure** must be explicitly called by an application or user (e.g., `EXECUTE procedure_name` or `cursor.callproc(...)`).
- A **Trigger** is invoked implicitly and automatically by the database engine whenever the specified event (`INSERT`, `UPDATE`, `DELETE`) occurs.
- Procedures can return values via OUT parameters; triggers cannot return values directly to the caller.

### Q13: What are SQL Bind Variables and why are they critical in web apps?
**Answer:**
Bind variables (e.g., `:name`, `:email`) pass user inputs separately from the SQL statement rather than concatenating strings directly into the query.
Two main reasons:
1. **Security**: Completely prevents **SQL Injection** attacks because user input is never interpreted as executable SQL code.
2. **Performance**: Allows the Oracle database engine to reuse parsed query execution plans in the Shared Pool, improving execution speed.

### Q14: What is `ON DELETE CASCADE` and where is it used in your schema?
**Answer:**
`ON DELETE CASCADE` is a foreign key constraint option that automatically deletes child records when the referenced parent record is deleted.
In our project:
- If a `CLUB` is deleted, all its `EVENT` and `MEMBERSHIP` rows are automatically deleted.
- If a `STUDENT` is removed, their `MEMBERSHIP` and `REGISTRATION` records are automatically removed.
This prevents orphaned foreign key references.

### Q15: What is the difference between DDL, DML, and DCL? Give examples from your project.
**Answer:**
1. **DDL (Data Definition Language)**: Defines and modifies the structure of database objects.
   - Examples: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE VIEW`.
2. **DML (Data Manipulation Language)**: Manages and modifies data inside tables.
   - Examples: `INSERT INTO STUDENT`, `UPDATE REGISTRATION`, `DELETE`, `SELECT`.
3. **DCL (Data Control Language)**: Controls privileges and permissions for database users.
   - Examples: `GRANT CONNECT, RESOURCE TO clubadmin`, `REVOKE`.
